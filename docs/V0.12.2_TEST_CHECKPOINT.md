# Vapor Loop 0.12.2 test checkpoint

Date: 2026-11-09  
Status: Browser prototype checkpoint; no FM-1 firmware build or hardware flashing

## Why this checkpoint exists

The 0.12.2 owner test established that Vapor Loop's musical systems have become large enough that the current long, single-page browser interface is obstructing reliable performance and evaluation. This document is the durable restart point if development pauses or the working conversation is interrupted.

The next phase is **not** another collection of musical features. It is an engine-state repair followed by an interface and observability reset.

## Test material reviewed

The owner supplied a 16 minute 26 second video of the 0.12.2 standalone browser build, performed primarily with the MPC as the MIDI controller.

The video's recorded soundtrack is extremely quiet (approximately -69 dB average and -57 dB peak in the uploaded file). The owner reports that the live monitored level was normal. Therefore, this recording is useful for confirming control flow and visible state, but it is not authoritative evidence for output gain, fine groove, or sub-beat timing.

## Behavior visibly confirmed

The video provides evidence that these systems are operating:

- Lead capture, Replay, Reply, and candidate interaction
- Automatic harmonic analysis after Lead capture
- An automatic C major result during the demonstrated capture
- Explicit manual key/scale override
- Candidate-specific harmonic context; Candidate A later retained E major
- Shared context reaching Reply, Bass, and Chord companion controls
- Chord Companion Root Follow and Phrase Follow producing active voices
- Poly Keys manual-pass recording
- Manual drum-grid editing and playback
- Bass controls and MIDI role routing
- Continued use of longer capture lengths, including the demonstrated eight-bar workflow

These observations do not prove FM-1 compatibility. They describe only the current browser simulation.

## Confirmed defect: selected engine is lost during transport use

At the start of the video, **FM Glass** is both selected and reported active by the compiled audio core. Later, the interface still shows FM Glass as the selection while the compiled-core readout reports **Sine Diagnostic**.

This is a real selected/active mismatch. The likely failure boundary is a transport or memory path reinitializing the voice and restoring the diagnostic engine instead of preserving the player's current engine selection.

### Required 0.12.3 repair

- Preserve the selected Lead engine across Capture, Finish, Replay, Reply, Keep, candidate selection, and manual-track recording.
- Make voice reset and transport reset separate operations where possible.
- Keep the selected-engine and active-engine readouts independent so future mismatches remain visible.
- Add regression coverage that exercises every transport operation with a non-default engine selected.
- Do not add new musical features in this release.

### 0.12.3 acceptance criteria

1. Select FM Glass, Virtual Analog Warm, or Karplus-Strong String.
2. Confirm the compiled core reports the selected engine.
3. Run Capture, Finish, Replay, Reply, Keep, candidate recall, Poly Keys recording, Bass recording, and Drum playback.
4. After every operation, the selected and active engine must still match.
5. Existing native, WebAssembly, AudioWorklet, Chromium, direct-file, and MIDI checks must remain green.
6. The owner repeats a short listening test before the next interface milestone begins.

## Timing observation: unresolved, not yet diagnosed

The owner reported that portions of the performance felt slightly out of time. The video does not provide strong enough audio evidence to identify a scheduler fault because:

- the captured audio level is extremely low;
- multiple transformed and companion parts can play together;
- the active synthesis engine changed unexpectedly;
- the current interface does not expose an event timeline or lane alignment;
- the long page makes it difficult to see transport state and musical controls simultaneously.

Do not label this a timing-engine defect yet. First repair engine persistence and expose timing visually.

## Interface decision

The current browser prototype has outgrown its one-page layout. HTML and WebAssembly remain suitable for the next stage; the problem is the information architecture, not the browser platform.

The browser build should become a focused **Vapor Loop Workbench** with one stable instrument window and no page-length performance workflow.

### Proposed 0.13.0 pages

| Page | Primary purpose |
| --- | --- |
| Play | Capture, Finish, Replay, Reply, Keep A/B/C, performance status, and timeline |
| Shape | Key/scale, Adventure, Phrase Architecture, groove, and variation intensity |
| Companions | Bass, Chord, and Drums with clear Off / Manual / Follow states |
| Setup | MIDI input and channel roles, split point, resolution, count-in, and capture correction |

### Controls that remain visible on every page

- Sound enabled/disabled
- Selected engine and compiled-core active engine
- Tempo and bar/beat position
- Active harmonic context and Auto/Manual source
- Current MIDI input and live destination
- Capture, Finish/Stop, Replay, and Reply
- Master stop/panic

### Timing and arrangement visibility

The Play page should add a shared bar/beat timeline with separate lanes for:

- Lead source
- Generated Reply or selected candidate
- Bass
- Chords / Poly Keys
- Drums

It should include a moving playhead, event starts, note lengths where practical, grid lines, lane mute/solo, and an Original-versus-Generated comparison. This will make synchronization testable instead of dependent on navigating menus and remembering hidden settings.

### Interface principles

- No new synthesis or composition features during the interface reset.
- Performance controls must not require vertical scrolling.
- Every track must visibly state whether it is Off, Manual, or Follow.
- Basic performance controls appear first; detailed editing belongs in an Advanced view.
- Selected values and values actually active in the compiled core must remain distinguishable.
- The existing portable C/WebAssembly musical core should be preserved rather than rewritten with the interface.

## Platform decision

Do not move directly to VST3 yet.

The current browser build already serves as the host simulation for the portable core. The FM-1 Workbench is not a general firmware GUI builder and will not solve this usability problem.

After the 0.13.0 Workbench interface and visual timing tests are stable, the preferred desktop order is:

1. Wrap the same portable C core in a standalone desktop application.
2. Validate audio, MIDI, transport, state, and interface behavior outside the browser.
3. Add the VST3 wrapper and DAW synchronization.
4. Validate macOS and Windows builds in real DAWs.
5. Begin the measured FM-1 hardware-port phase only after the host implementations are stable and a recovery procedure is established.

## Agreed release sequence

| Release | Scope | Gate |
| --- | --- | --- |
| 0.12.3 | Preserve synthesis-engine state and add transport regression tests | Automated checks plus short owner listening test |
| 0.13.0 | Vapor Loop Workbench interface reset and visual multi-lane timeline | Owner can perform and test without long scrolling |
| Later host milestone | Standalone desktop wrapper using the shared C core | Desktop audio/MIDI/state validation |
| Later plugin milestone | VST3 wrapper and DAW transport integration | macOS and Windows DAW validation |
| Hardware phase | FM-1 target investigation, build, recovery, and controlled flashing | Separate authorization and one designated test unit |

## Restart checklist

When development resumes:

1. Open this checkpoint before adding features.
2. Reproduce the FM Glass-to-Sine Diagnostic reset.
3. Inspect voice initialization in Capture, Replay, Reply, Keep/candidate, and manual-track paths.
4. Implement 0.12.3 engine preservation.
5. Add non-default-engine transport regression tests.
6. Run the complete automated test matrix.
7. Issue a small downloadable 0.12.3 build for owner validation.
8. After approval, design and implement the 0.13.0 Workbench without changing musical behavior.
9. Use the new visual lanes and mute/solo controls to investigate the reported timing feel.
10. Continue to prohibit FM-1 flashing until the hardware phase is explicitly authorized.

## Deferred musical features

The following ideas remain valid but are intentionally paused until the repair and interface milestones are complete:

- richer Bass and Chord resolutions and movement patterns;
- advanced chord voicings, inversions, strums, and arpeggiation;
- expanded drum synthesis and classic-machine-inspired kits;
- effects, including modulation, delay, reverb, shimmer, tape, wow/flutter, and noise;
- deeper synthesis parameters;
- expanded manual sequencing and editing;
- further genre-aware Phrase Architecture.

This checkpoint supersedes any informal assumption that new musical features are the immediate next step.
